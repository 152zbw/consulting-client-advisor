# 客户反馈处理

把反馈转成可验证的工作，不先答应全部修改，也不先防御。

## 澄清分支

- “不够落地”：请举一个拿到成果后仍无法完成的动作。缺步骤则补路径；缺责任安排则讨论分工；缺样例则核查工具要求；要持续陪跑则检查是否新增服务。
- “不是我们想要的”：定位到具体段落/表格及原目标，询问期望用途和差异；核实是否我方误解、客户需求变化或双方未确认。
- “数据不对”：核实记录、版本、时期、口径和计算；实际错误优先纠正，原因未明不直接反驳。
- “领导不认可”：询问具体评价、决策标准及使用场景，不臆断领导偏好；必要时建议共同澄清。

## 工作表

|ID|客户原话及出处|文件版本/位置|问题分类与依据|建议修改|验证方式|范围及授权|负责人/时间/状态|
|---|---|---|---|---|---|---|---|

每条意见有处置：修改、解释、待澄清、提出变更或保留分歧。拆开一条意见中的不同要求，避免遗漏。修改记录包含实际改动与仍未验证部分，不声称未执行的改动已完成。

如有原文，给针对位置的修改建议或替换稿；只有口头反馈时先定位，不编造页码。验收依据未知时，提出待确认的标准，不降低已约定标准。

## 回复结构

感谢并准确复述具体问题 → 已核实的判断 → 各类问题分别怎么处理 → 需澄清的事项 → 下次确认安排。只有确有我方问题才承认该问题，不承认未经核实的全部责任；同时避免把应纠错事项说成关系性赠送。
